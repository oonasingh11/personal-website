How do computers really work? Compilers? Interpreters?

are computers just magic

Hello all.

Welcome (and welcome back).

I’ve decided that 2025 will be my year of understanding everything at its most fundamental level. I’ve done plenty of freelance hacking, built apps, and fiddled around here and there—but I’ve realized I never resolved a core question: how do computers actually run my code?

Sometimes, technology does feel like magic. As Arthur C. Clarke famously put it, “Any sufficiently advanced technology is indistinguishable from magic.” And in a world where LLMs keep evolving, that “magic” can feel even more beyond comprehension. I’m not entirely comfortable with just accepting it. I want to see what’s behind this curtain, especially if I keep building AI tools.

So that’s why I’ve decided to build my own compiler. But first, I’m starting with an interpreter. These two tools do roughly the same job—translating code into actions the computer can understand—but in different ways.

  • Interpreters read code line by line, turning statements (like x = 5) into immediate actions. It’s like an instant translation service, going sentence by sentence.
  • Compilers take an entire program, convert it all at once into a new form (like a .exe on Windows or “bytecode” for Java), and then you run that newly generated file whenever you want, without needing your original code again.

For a quick example: if I type [print 2 + 3] in an interpreted language, the interpreter splits it into tokens (PRINT, NUMBER(2), PLUS, NUMBER(3)), figures out that I want to add 2 and 3, and prints 5 right away. A compiler would first convert my entire program into machine code that can directly do the math whenever I run the compiled file.

In this brave new world, where AI can spit out a complete script swiftly, I feel wary about how little I understand the lower layers. I don’t want to keep stacking “magic” on top of “magic.” Otherwise, working with LLMs feels akin to building a house on shaky foundations; you can do it — it might work, but it’s dubious (don’t take architectural advice from me; I’m just a random person on the internet).

In short, I don’t want to pile new abstract understandings of programming onto other ideas.

So here’s the plan: build a small language that can handle basic statements, expressions, and maybe even simple functions, then write an interpreter that does three big things:

  • Lexing/Tokenizing: Take raw text and split it into meaningful pieces (e.g., LET, ASSIGN, IDENTIFIER, NUMBER).
  • Parsing: Organize those pieces into an internal structure—an Abstract Syntax Tree (AST)—that shows the relationships (e.g., “set variable x to 5”).
  • Evaluation: Execute whatever the AST says to do, step by step, so I can see the exact flow from text to actual output on my screen or console.

It might not be the most glitzy project, but I’m betting I’ll learn more from this than from another year’s worth of gluing libraries together. Once I know how to build an interpreter - and I’ve done it well, I will build a compiler.

If you’ve ever wondered how your code actually gets turned into the actions you see on screen (or in the console), then maybe this newsletter series is for you. I’m excited, a bit nervous, and more than a little curious to finally make this magic seem more like tech.

Here’s hoping we all come away with a deeper understanding of how our code goes from text to execution. And, in the end, candidly, I’d rather rely on knowledge than just magic, no matter how advanced our tools become.

Until next time.

Bye.
